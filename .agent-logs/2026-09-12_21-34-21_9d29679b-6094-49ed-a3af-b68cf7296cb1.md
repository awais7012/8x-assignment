## 0. What Higgsfield actually is (so you don't build the wrong thing)

Higgsfield is a multi-model AI creative studio: text/image-to-video and
text-to-image generation, wrapping several third-party models (Kling, Veo, Sora 2,
Seedance) plus in-house tools (Cinema Studio for camera-controlled video, Soul ID for
character consistency, motion transfer/"Genjutsu", audio dubbing/lip-sync, a
Marketing Studio for ad creative). It's credit-based, multi-tier pricing, and — this
matters — **the onboarding quiz is not really personalization for your creative
experience.** It's a lead-qualification funnel: answer a few questions about who you
are and what you want → confetti → a fake-scarcity "personal" discount code with a
countdown timer → dumped on the pricing page. That's worth knowing because it means
we are free to make our version of the quiz *actually* do something useful
(informing the workspace/defaults) instead of copying the manipulative part. That's a
legitimate, defensible product judgement call for the write-up: "we kept the
onboarding shape, we cut the dark-pattern paywall funnel because it doesn't
demonstrate engineering and actively degrades UX."

Full surface area (Cinema Studio, Marketing Studio, Audio/dubbing, Effects,
Enterprise workspace, Supercomputer/MCP) is not buildable in 24h and should not be
attempted. See scope cuts below.

## 3. Data model (Prisma schema, sketch)

```prisma
model User {
  id            String   @id // Clerk user id
  email         String   @unique
  createdAt     DateTime @default(now())
  profile       UserProfile?
  generations   Generation[]
  creditsBalance Int     @default(50) // cosmetic starting balance
}

model UserProfile {
  id           String   @id @default(cuid())
  userId       String   @unique
  user         User     @relation(fields: [userId], references: [id])
  usageContext String   // "personal" | "team"
  goal         String   // "avatars" | "cinematic" | "marketing" | "ugc" | "explore" | "automation"
  experience   String?  // "beginner" | "intermediate" | "pro" — optional 3rd Q if time allows
  createdAt    DateTime @default(now())
}

model Generation {
  id          String   @id @default(cuid())
  userId      String
  user        User     @relation(fields: [userId], references: [id])
  type        String   // "image" | "video"
  prompt      String
  refImageUrl String?
  resultUrl   String?
  status      String   // "queued" | "processing" | "complete" | "failed" | "quota_exceeded"
  provider    String   // which backend actually served it, for transparency/debugging
  creditsCost Int
  createdAt   DateTime @default(now())
}
```

Why `provider` is on the row: when free-tier quota forces a fallback (§5), you want
to be able to show — even just in an admin/debug view — what actually served each
result. Also makes the demo narratable: "here's what happens when the primary quota
is out."

Why `UserProfile` is separate from `User`: the quiz answers are inputs to
personalization logic, not identity. Keeping it a separate model makes it trivial to
extend later (e.g., re-running the quiz) without touching auth-critical fields.

## 4. The onboarding quiz — what it's *for*

Screens (matches screenshots 1 & 2):
1. "How do you plan to use \<product\>?" — Personal / Team
2. "What do you want to achieve?" — multi-card select: Avatars & product visuals /
   Cinematic visuals & AI films / Just exploring / High-converting marketing / Viral
   content & UGC / Automate workflows

Real Higgsfield uses this to route you into a discount funnel. **We use it to set
workspace defaults** — this is the actual product improvement over the original and
the thing to say in the walkthrough:

- `goal = "avatars"` → workspace opens on Image tab, prompt placeholder suggests
  portrait/product-shot prompts
- `goal = "cinematic"` or `"ugc"` → workspace opens on Video tab
- `goal = "explore"` → show a curated example-prompt gallery instead of a blank
  input (cold-start problem — a blank prompt box is the #1 activation killer for
  first-time users, and Higgsfield's own reviews mention prompting being the hard
  part)
- `usageContext = "team"` → currently no functional difference (team features are
  cut) — but store it; label it honestly in UI copy as "coming soon" rather than
  faking a team switcher

No LLM call needed to process quiz answers — it's a 2-question form mapping directly
to an enum-driven default. **Do not build a "knowledge graph" or run a small model
over onboarding answers to classify the user.** Two multiple-choice answers do not
need an inference pipeline; a switch statement is strictly better here: it's free,
instant, debuggable, and has zero failure modes. Spending build time on an ML
classifier for 2 categorical inputs is the single highest-risk scope trap in this
brief — flag and cut it immediately if it comes up again.

## 5. Generation backend — the part that actually matters

**Constraint recap**: $0 budget, must survive a live demo hit by unknown judges,
Gemini's free tiers are real but thin and shared per-project (as low as 20-50
requests/day on stronger models, resetting midnight Pacific). A demo that 429s in
front of a judge is a failed demo, not a minor bug.

### Provider chain (in priority order, with automatic fallback)

1. **Primary image**: Gemini 2.5 Flash Image ("Nano Banana") via Google AI Studio
   API key. Free tier exists but is rate-limited (RPD in the tens-to-hundreds,
   varies by model/day — check current limits at build time, they move). Good
   enough quality for a demo, genuinely free.
2. **Fallback image**: Pollinations.ai (fully free, no key, no rate-limit wall
   worth worrying about, lower/inconsistent quality). Use automatically when
   primary 429s or errors.
3. **Video**: this is the hard one — there is no free, no-signup, reliable
   text-to-video API as of this build. Options, pick based on what's actually live
   when you build:
   - A free-credit trial on a hosted video API (Runway/Luma/Kling all have small
     signup credit grants) used sparingly and only as primary, same fallback
     pattern as above
   - If nothing free is reliable: **video generation runs in "queued" state and
     resolves to a curated set of pre-generated sample clips** matching the
     prompt's rough category (portrait/product/landscape/action), clearly labeled
     in the UI as a demo/sample result. This is an honest, disclosed simulation —
     not a silent fake. Label it in the UI: "Sample output — live video generation
     runs on limited free capacity."
4. Every generation call is wrapped: try primary → on failure/429, try fallback →
   on failure, mark `status: "quota_exceeded"` and show the user a clear, honest
   in-product message, not a spinner that hangs forever or a raw error.

### Why this design, explicitly

- A single point of failure on a rate-limited free API is the single biggest risk
  to a live judged demo. Fallback chains are not gold-plating here — they are the
  actual reliability requirement given the constraint.
- Faking video output is only acceptable if disclosed in the UI. Silently serving
  a canned video as if it were generated would misrepresent what was built — call
  it what it is and it becomes an honest, disclosed design decision instead of a
  potential integrity problem.
- Do not attempt to self-host a video model (ComfyUI/SDXL/AnimateDiff) for this
  build. No free GPU host reliably survives cold-start + public traffic in a 24h
  window with $0 budget; that path burns hours on infra with a high chance of
  still failing live.

### Rate-limit UX (build this — it's part of the core spine, not a stretch goal)

When quota is exhausted:
- Show it on the generation card itself, not a toast that disappears
- Offer the automatic fallback result if one exists, labeled as such
- Never leave a spinner with no timeout — cap wait time and resolve to a failure
  state

## 3. What to capture

Write captures to `.agent-logs/` in the repo root. These are committed and ship with
your repo, publicly, so treat them as part of the submission.

**We want the prompt and the final response. Nothing in between.**

Not the thinking. Not the tool calls. Not the intermediate steps, the file reads, the
diffs, or the retries the model made on its own. Just: what you asked, and what came
back at the end of that turn.

Capture, per turn:

- The prompt, verbatim and in full. No truncation, no paraphrase, no cleanup.
- The final response for that prompt, in full, including the ones where it got it wrong.
- A UTC timestamp.
- The model name, so a switch mid-build is visible.

Do not:

- Add `.agent-logs/` to `.gitignore`. It ships with the repo.
- Edit, tidy, summarise, or delete an entry after the fact. A messy honest log scores
  better than a clean one, and we can tell the difference.

Commit the logs as you go, interleaved with the code they produced, not in one dump at
the end. The commit order shows the order you actually worked in.
